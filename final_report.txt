1. Overview

This system is a FastAPI-based multi-tenant WhatsApp AI commerce backend.

It currently supports:
- customer commerce conversations over WhatsApp
- vendor-side order operations and business intelligence over WhatsApp
- planner-based agent execution with tools, memory, workflow state, and second-pass reasoning
- event-driven revenue automation
- MongoDB-backed tenant isolation, analytics, and operational tracking
- JWT-protected API access for business and admin surfaces

The core agentic architecture remains intact:
- inbound webhook
- business and user resolution
- controller
- planner
- tool execution
- memory and state updates
- outbound messaging

No hardcoded chatbot flow replaced the planner/tools design.

3. Meta Webhook and Inbound Flow

Webhook route:
- app/routes/whatsapp.py

Inbound flow:
1. `GET /webhook/whatsapp`
   - verifies Meta webhook challenge
   - checks `hub.mode`, `hub.verify_token`, `hub.challenge`

2. `POST /webhook/whatsapp`
   - requires JSON payload
   - validates webhook signature with `X-Hub-Signature-256`
   - uses `META_APP_SECRET` for HMAC verification
   - parses Meta inbound messages and Meta delivery status events
   - deduplicates inbound messages using:
     - in-memory recent cache
     - Mongo `webhook_dedupe`
   - resolves business by WhatsApp number or vendor phone
   - tracks last user interaction timestamp
   - routes message to planner-based agent controller
   - sanitizes reply
   - sends outbound reply through Meta dispatch layer

Delivery status handling supported:
- sent
- delivered
- read

These statuses are written back into outbound dispatch records.

5. Session Window Enforcement

The system now tracks last user interaction timestamps in conversation state.

Behavior:
- if the customer is inside the 24-hour WhatsApp session window, normal free-text send is allowed
- if outside the window, free-text send is blocked
- the dispatch is marked `template_required`
- no invalid free-text message is sent

This enforcement lives below the business send helpers so it applies consistently.

6. Messaging Retry and Reliability

Meta send retries are no longer blind.

Current retry model:
- retry only safe network and retryable provider failures
- exponential backoff
- queued retry state persisted in Mongo
- later replay through notification retry processing

Non-retryable failures are marked failed immediately.
