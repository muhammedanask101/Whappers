4. AUTHENTICATION AND AUTHORIZATION
================================================================================

Auth implementation location
- `app/services/auth.py`

Roles
- `superadmin`
- `business_admin`
- `vendor`

Token model
- Access token:
  - custom HS256-style JWT implementation
  - short-lived
  - 15 minute expiry
- Refresh token:
  - custom HS256-style JWT implementation
  - 30 day expiry
  - persisted in Mongo collection `refresh_tokens`
  - sent as httpOnly cookie `wa_refresh_token`

Auth storage collections
- `users`
- `refresh_tokens`
- `subscriptions`
- `onboarding_states`

Auth capabilities implemented
- password hashing with bcrypt
- credential login
- refresh flow
- logout flow with refresh-token revocation
- current-user extraction from bearer token
- legacy `x-admin-token` bridge for compatibility
- role checks on API endpoints
- tenant scope enforcement for business-scoped endpoints
- subscription feature checks for gated features

Important technical note
- JWT handling is custom, not library-backed.
- There is no dependency on `PyJWT` or `python-jose`.
- This keeps dependencies minimal but moves signature/parsing correctness responsibility into project code.

Superadmin seeding
- If `SUPERADMIN_EMAIL`/`SUPERADMIN_PASSWORD` are set, those are used.
- Fallback uses `MANAGER_EMAIL`/`MANAGER_PASSWORD`.
- This is seeded in `seed_auth_entities()`.

Legacy compatibility
- `authenticate_legacy_admin_token()` maps the old `ADMIN_TOKEN` to a superadmin identity.
- This preserves access for older admin clients using `x-admin-token`.

Security posture summary
- Better than previous shared-token-only model because new APIs enforce per-user role and tenant scope.
- Still transitional because the legacy `/admin/*` token API remains mounted.

10. WHATSAPP FLOW
================================================================================

Entry route
- `app/routes/whatsapp.py`

Endpoint
- `POST /webhook/whatsapp`

Behavior
- validates Twilio request in production-like conditions
- resolves business by recipient WhatsApp number or sender vendor phone
- classifies sender as `vendor` or `customer`
- invokes `process_incoming_message()` from agent controller
- sends reply via `send_whatsapp_message_async()`
- rate limits incoming requests
- deduplicates repeated webhook deliveries in memory

Business continuity status
- WhatsApp flow remains mounted and was not intentionally altered as part of the dashboard extraction.
- This was a core preservation requirement and appears respected structurally.

Operational caveat
- Deduplication state is in-process memory only.
- It will not survive restarts or scale-out horizontally without additional coordination.

================================================================================

Current codebase status
- The project is no longer using backend-rendered dashboard HTML.
- The backend now contains a meaningful API-only dashboard layer with auth, RBAC, tenant scope, onboarding, and subscription state.
- A new Next.js dashboard app has been scaffolded around that API layer.

  - backend = API + agent + business logic
  - frontend = UI

- Functional verification is incomplete due missing installed tooling in this environment.

Bottom line
- The current code is a real mid-to-late transition state toward the target production architecture.
- It is significantly cleaner than the previous mixed backend UI design.
- It is not yet a fully finalized, single-surface, fully-verified production dashboard stack.
