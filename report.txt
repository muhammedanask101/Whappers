WHATSAPP AGENT IMPLEMENTATION AND CURRENT WORKING REPORT
Generated from repository inspection on 2026-03-29

Purpose
- This report documents the current implementation of the WhatsApp agent for sales, order management, and customer support.
- It is intended for debugging and traces what the code currently does, how the main flows are wired, what data is persisted, what is currently observable from the local environment, and what implementation mismatches or hotspots are present.
- No application code was changed while creating this report.

===============================================================================
1. HIGH-LEVEL SYSTEM SHAPE
===============================================================================

Current backend stack
- FastAPI backend in `app/main.py`.
- Twilio WhatsApp webhook entrypoint in `app/routes/whatsapp.py`.
- MongoDB is the primary persistence layer in current code via `app/db/mongo.py`.
- A legacy SQLite database file `commerce.db` still exists locally, but the active backend code does not use it for runtime operations.
- Session-based manager dashboard is rendered as server-generated HTML in `app/routes/admin.py`.
- Token-protected JSON admin API lives in `app/routes/admin_api.py`.
- A separate Next.js dashboard exists in `dashboard/`, consuming the admin API.
- An autonomous agent engine lives under `app/services/agent/`.
- Analytics, recommendations, customer profiling, and automation live under `app/services/intelligence/`.

Primary business domains implemented
- Sales:
  product catalog browsing, product details, recommendations, vendor catalog management, promotions, offers, events, broadcasts.
- Order management:
  cart building, address capture, checkout, order status retrieval, vendor order status updates, vendor notifications, delivery-progress nudges.
- Customer support:
  support ticket creation, support ticket updating, ticket resolution, vendor notification of support issues, recovery follow-ups.

Primary runtime roles
- Customer:
  browses products, builds cart, shares address, places order, asks order status, raises support issues, receives support and automated follow-ups.
- Vendor:
  receives order notifications, updates order status by replying in natural language, manages products and offers, updates business profile, sends broadcasts, resolves support tickets.
- Manager:
  signs into HTML dashboard, manages businesses and products, views recent orders.
- Admin token holder:
  uses JSON APIs for business listing, orders, usage, support, traces, and dashboard analytics.

2. BOOT PROCESS AND APP STARTUP
===============================================================================

Startup sequence in `app/main.py`
- Reads `.env` manually with `load_env_file()` before app creation.
- Initializes Mongo-backed DB via `init_db()`.
- Creates FastAPI app titled `WhatsApp Conversational Commerce Agent`, version `2.0.0`.
- Adds SlowAPI rate limiting middleware.
- Adds session middleware for manager login.
- Mounts routers:
  `/onboard`
  `/webhook/whatsapp`
  manager HTML routes
  admin JSON API routes
- On startup:
  initializes Mongo DB handle into `app.state.mongo_db`
  seeds manager user if manager env credentials exist
  starts one daemon automation thread running `run_automation_cycle()`
- Exposes `/health` returning `{"status": "ok"}`.

Operational implication
- The backend assumes Mongo is configured and reachable at import/startup time.
- The automation thread is always started once when the app starts.

5. ROUTING LAYER
===============================================================================

5.1 WhatsApp webhook route
File
- `app/routes/whatsapp.py`

Behavior
- Expects Twilio form fields:
  `Body`
  `From`
  `To`
  `MessageSid`
- Rate limit: `10/minute`
- If `ENV=prod`, validates Twilio signature using `RequestValidator`
- Rejects missing `Body` or `From`
- Normalizes sender and recipient with `normalize_phone()`
- Deduplicates webhook calls for 180 seconds using:
  `MessageSid`, or fallback `sender|lower(body)`
- Resolves business by:
  1. matching Twilio recipient against a business `whatsapp_number`
  2. otherwise matching sender against `vendor_phone`
- Determines role:
  `vendor` if sender equals business vendor phone
  else `customer`
- Calls `process_incoming_message()`
- Sanitizes reply with `safe_user_facing_text()`
- Sends reply back via Twilio using the business-specific `whatsapp_number` as sender

Debug implications
- Twilio auth token is required at import time. If missing, importing this route raises immediately.
- Business resolution can fail if the incoming numbers do not exactly match normalized stored values.
- Duplicate webhook suppression may hide repeated deliveries during testing.

7.3 Order creation and pricing
File
- `app/services/order.py`

Order creation sequence
1. `calculate_order_pricing()`
2. create `OrderRecord`
3. update customer profile using preview data
4. trigger event `order_created`
5. insert Mongo order document with:
   `items`
   `line_items`
   `total`
   `status=pending`
   address
   timestamps

Pricing logic
- Uses product catalog map
- Uses active promotions/events as pricing adjustments
- For each item:
  fetch base price
  apply product `offer_price` if lower
  apply best active adjustment if better
  compute line total
- Invalid or unknown products are silently skipped during pricing

Important order status transitions
- `pending -> accepted/rejected`
- `accepted -> out_for_delivery`
- `out_for_delivery -> delivered`

Vendor actionable order lookup
- If specific order id given, use it.
- Else infer latest actionable order based on desired status:
  for accept/reject: latest pending
  for out_for_delivery: latest accepted
  for delivered: latest out_for_delivery

Customer support creation behavior

8.2 Support context inspection
- `inspect_support_context` fetches latest tickets for:
  current open ticket id if present
  else current customer
  vendor can pass customer phone

  sends a follow-up asking customer to reply if anything changed

9. AGENT ENGINE: HOW THE AGENT ACTUALLY WORKS
===============================================================================

9.1 Main message flow
Entrypoint
- `process_incoming_message()` in `app/services/agent/controller.py`

Sequence
1. Load conversation state with `get_state()`
2. Try `handle_pending_action()`
   currently this function is effectively a no-op and always returns `None`
3. Detect/update language style
4. Load customer profile
5. Load learning profile
6. Run preliminary intent analysis
7. Select LLM cost tier
8. Build memory payload:
   lightweight for safe cheap browse/general cases
   full otherwise
9. Update last active
10. Record `incoming_message` event
11. Run autonomous agent loop with `run_agent()`
12. Sanitize final reply
13. Persist updated state
14. Save chat history turn
15. Store semantic memories
16. Update learning profile
17. Record sentiment feedback signal
18. Record `agent_reply` event
19. Record metrics
20. Log agent trace
21. Return reply

14. IMPORTANT DEBUG HOTSPOTS AND IMPLEMENTATION INCONSISTENCIES
===============================================================================

14.1 Duplicate function definitions in `app/services/vendor.py`
- The file contains duplicate later re-definitions of:
  `format_offer_preview`
  `notify_customer_order_update`
  `generate_vendor_acknowledgement`
  `_notify_vendor_support_ticket`
- In Python, the later definitions win.
- This means earlier behavior in the same file is dead/overridden.
- Anyone debugging this file must read the bottom-most definitions as the effective ones.

14.2 Duplicate function definitions in `app/services/agent/tools.py`
- The file contains earlier and later definitions of:
  `_tool_collect_address`
  `_tool_search_catalog`
- The later definitions override the earlier ones.
- Effective live behavior is the later stricter address validator and the later broader browse-search recovery logic.
- This file is a major debugging hotspot because reading top-to-bottom naively is misleading.

14.3 `handle_pending_action()` is effectively unused
- `app/services/agent/executor.py` returns `None`.
- Pending action infrastructure exists in state but does not currently drive any real workflow.

14.4 Admin dashboard route protection inconsistency
- Most `/admin/*` routes require `x-admin-token`.
- `/admin/dashboard/{business_id}` does not.

14.5 Twilio auth token required at import time
- In `app/routes/whatsapp.py`, missing `TWILIO_AUTH_TOKEN` raises during import.
- This can break app startup before handling any requests.

14.6 Customer notification style source in vendor order status updates
- `vendor_update_order_status` calls:
  `notify_customer_order_update(updated.customerPhone, updated, style_hint=style, ...)`
- `style` here is the vendor conversation style, not the customer's stored style.
- Result:
  customer order-status updates may be sent in the vendor's language style, not the customer's.

14.7 Onboarding route creates business with same WhatsApp and vendor phone
- `app/services/onboarding.py` uses the same input phone for both.
- Useful for demos, but simplistic for real multi-number setups.

14.8 Dashboard order loading inefficiency
- Next dashboard loads all orders then filters client-side.

14.9 Live secrets in `.env`
- Operational risk, not functional bug.
- Relevant for debugging because accidental real sends and external API usage can happen.

14.10 Mongo unavailability blocks true runtime verification here
- Code is Mongo-first.
- This environment could not verify current remote documents.

15. END-TO-END FLOW SUMMARIES
===============================================================================

15.1 Customer sales browse flow
1. Customer sends WhatsApp message like "What products do you have?"
2. Webhook resolves business and role=customer.
3. Agent controller loads state/profile/learning and analyzes intent.
4. Cheap path likely classifies as browse.
5. Planner often chooses `search_catalog`.
6. Effective search tool handles generic browse specially:
   no narrow DB search
   broader ranked listing
7. Reply is localized and sent through Twilio.
8. Learning profile is updated with tool outcome and viewed products.
9. Trace and metrics are recorded.

15.2 Customer order placement flow
1. Customer asks for items.
2. Agent chooses `manage_cart`.
3. Tool parses product/qty, resolves products, updates cart state.
4. If address missing, workflow goes to `collect_address`.
5. Customer sends address.
6. Effective `_tool_collect_address` validates address-like structure.
7. If valid, workflow moves to `ready_to_checkout` and returns preview.
8. Customer confirms.
9. Planner/cheap path chooses `checkout_order`.
10. Order is created, profile updated, order event recorded.
11. Vendor notification is attempted.
12. Cart/workflow are cleared.
13. Customer receives localized order confirmation.

15.3 Customer order-status flow
1. Customer asks where order is.
2. Agent classifies `order_status`.
3. Tool `get_order_status` uses explicit id, or state `last_order_id`, or latest order.
4. Customer receives localized summary of status, items, and total.

15.4 Customer support flow
1. Customer describes issue.
2. Agent classifies `support`.
3. Support-oriented strategy disables upsell.
4. Agent may inspect support context first.
5. Tool `create_support_ticket` updates existing unresolved ticket or creates a new one.
6. Vendor support notification is sent.
7. Ticket id is stored as `open_ticket_id`.
8. Automation may later follow up if unresolved.

15.5 Vendor order update flow
1. Vendor replies naturally with terms like accepted, dispatch, delivered.
2. Webhook resolves role=vendor.
3. Policy builds vendor status candidates.
4. Cheap path may skip LLM and choose `vendor_update_order_status`.
5. Tool finds latest actionable order for target transition.
6. Transition is validated against allowed status graph.
7. Order is updated in DB.
8. Customer gets status update message.
9. Vendor gets localized acknowledgement.
